# コードレビュー / 命名・コメントルール

> 背景・出典・NG例の詳細: [review-techniques.md](./review-techniques.md)

## レビューコメントの書き方

- 動くコード片を添えて代替案を示す。「直してください」より「こう書けます」。実際に手元で試してから書き、破綻案をレビュー段階で排除する
- 強制力を接頭辞で明示する

  | 接頭辞 | 意味 |
  |---|---|
  | 必須 / must | マージ前に対応必須 |
  | 好みです | 採用しなくてもOKな提案 |
  | ※FYI | 情報共有のみ |
  | ※前回レビュー時に指摘すべきでした | 過去PRに遡るが今でも修正したい |
  | nit | 些細な指摘（タイポ等） |

- トレードオフを開示する。推し進めない選択肢にも触れ、相手が判断材料を持てるようにする
- 結論より「なぜ」を書く。ライブラリのデフォルト挙動、過去インシデント、エッジケース、公式ドキュメントへのリンク。レビューコメントは将来の検索対象になる
- セキュリティ・障害対応では動作検証の証跡（攻撃コード、エラー文言、再現手順）を残す

## 命名

- 否定形の AND 連結より filter チェーン。意味単位で分解し、`'all'` は各 filter 内で早期に許可する
- 他動詞の進行形を疑う。`editingConfig` → `configToEdit`、あるいは修飾自体が不要なら `config`
- アンダースコア接頭辞は「未使用」のサイン。`_bannersResponse` を使っているなら接頭辞を外す。値が不要ならその fetch 自体をやめる

## コメント

- **何をしているか** は良い識別子で表現する。コメントに書かない
- **なぜそうしているか** が非自明なときだけ書く（隠れた制約、過去のバグ対応、surprising な挙動）
- 現在のタスクや「used by X」のような変動する情報は書かない。PR 説明欄に書く

## レビューで一貫して見る観点

1. コード片を添えた代替案になっているか
2. トレードオフを開示しているか
3. プラットフォームへの回帰（useEffect 回避 / `'use client'` を増やさない / HTML 標準・semantic role）
4. レイヤを跨いだ視点（フロントPRでもバックエンドAPIの形、上流ライブラリの差分）
5. fail-silent を許していないか（→ [quality.md](./quality.md)）
6. a11y とテスト安定化を同時に達成しているか
